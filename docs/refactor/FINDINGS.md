# Расхождения плана с текущим кодом

Зафиксировано при разборе `refactoring_plan.md` по исходникам `aether`, `packwiz-plugin`,
`curseforge-plugin` (2026-09-20). Новые расхождения дописывать сюда, а не в карточки задач.

Колонка «Статус» обновлена 2026-09-20 после решений владельца по всем 9 вопросам
(`OPEN_QUESTIONS.md`). «Закрыто» означает, что расхождение снято принятым решением;
«открыто» — что оно остаётся и учитывается в конкретной задаче.

| # | Расхождение | Влияние | Статус | Куда попало |
| --- | --- | --- | --- | --- |
| F-1 | packwiz — **не** content provider. `packwiz/capabilities.json` объявляет только `importers` и `updaters`; ядро вызывает его через `Importer::import` / `Updater::update`. План (шаг 2.4.3) описывает packwiz как провайдера с `resolve_install_plan`, но не говорит, что станет с importer/updater-путями и с «обновлением при запуске». | Высокое | закрыто решением Q1 (packwiz не переписывается в этом проходе) | Q1, T-2.4.3.D |
| F-2 | `curseforge-plugin` **уже существует** (`Z:\Projects\git\curseforge-plugin`), вопреки формулировке плана «он ещё не существует»: незакоммиченный скелет (git без коммитов), `capabilities.json` в устаревшей схеме (`provider_data_content_id_field`, `searchHandler`/`installHandler` — таких полей нет в `ProviderHandlersDto`), edition 2021, `extism-pdk 1.4`/`extism-convert 1.13`, зависимость `aether-core-plugin-api 0.1.0` из репозитория `MangriMen/aether-core`. | Среднее | закрыто решением Q3 (CF отложен) + Q5 (репозиторий API) | F-7, T-2.4.2.A |
| F-3 | Порядок внутри Фазы 1.5 противоречит её же обоснованию: план ставит 1.5.1 (`ro:` на `instances_dir`) перед 1.5.2 (миграция packwiz на `write_instance_file`), хотя сам пишет, что `ro:` раньше миграции ломает packwiz. Задачи здесь идут в обратном порядке: `T-1.5.A` (packwiz) → `T-1.5.B` (`ro:`). | Среднее | закрыто решением Q2 (порядок инвертирован) | Q2 |
| F-4 | `LoadConfig::Extism.memory_limit` документирован как «в байтах» (`plugin_manifest.rs`), а `Manifest::with_memory_max(u32)` принимает **страницы по 64 KiB**. Плюс `xtask` плагинов всегда генерирует `memoryLimit: null` — то есть значение из манифеста сейчас не задаётся никем. | Среднее | закрыто решением Q8 и реализовано в T-0.1 (байты в манифесте, конвертация вверх в ядре, дефолт 256 MiB; `xtask` читает `memory_limit` из `[package.metadata]`) | Q8, T-0.1 |
| F-5 | Терминология плана ≠ код: план говорит `ContentFile` / `pack_storage.save_content_file`. В ядре это `PackFile` и `PackStorage::update_pack_file` / `update_pack_file_many` / `find_by_provider_id` / `remove_pack_file`. `ContentFile` тоже существует, но это другой тип. | Низкое | открыто — учитывается в T-2.3.B | T-2.3.B |
| F-6 | `FileHash { Sha1, Sha512 }` из плана не покрывает реальность: индекс packwiz использует `hash-format = sha256` (и др.), CurseForge отдаёт sha1/md5. В ядре есть только `sha1_smol` (`shared/hash`), крейтов `sha2`/`md-5` нет. `Request::with_sha1` — единственная проверка хеша в `RequestClient`. | Среднее | закрыто решением Q6 (Sha1/Sha256/Sha512, sha2; md5 отложен) | Q6, T-2.1.A |
| F-7 | Плагины тянут `aether-core-plugin-api` по git из **разных** источников: packwiz — `github.com/MangriMen/aether` v0.2.0, curseforge — `github.com/MangriMen/aether-core` v0.1.0 (в монорепозитории сейчас 0.2.0). Схема манифеста продублирована в `xtask` каждого плагина (`xtask/.../domain/manifest.rs`). Любое изменение контракта = релиз ядра → обновление зависимости в плагине → пересборка плагина. | Высокое | закрыто решением Q5 (канонический MangriMen/aether-core, пины на теги) | Q5, T-1.4 |
| F-8 | `ContentProviderCapabilityMetadataDto` содержит булевы `supportsInstallAtomic` / `supportsInstallModpacks`, а `ProviderHandlersDto` — `installAtomic` (обязателен) и `installModpack`. Под новый контракт это надо заменять, и это ломает все существующие `capabilities.json`. | Среднее | открыто — решается в T-2.4.4 | T-2.4.4 |
| F-9 | Общий `reqwest::Client` (`apps/desktop/src/core/app/container.rs:132`) строится без `redirect`-политики, то есть по умолчанию следует до 10 редиректов. Host-функция `http_get` (0.6) должна строить **отдельный** клиент с `Policy::none()`, а не переиспользовать общий. | Высокое | открыто — решается в T-0.6 | T-0.6 |
| F-10 | Трейт `ContentProvider` в коде имеет метод `fn metadata(&self) -> &ContentProviderCapabilityMetadata`, которого нет в листинге 2.2 плана. Его надо сохранить — на нём держится реестр провайдеров (`CapabilityRegistry`). | Низкое | открыто — учтено в T-2.2 | T-2.2 |
| F-11 | `execute_async` (`block_in_place` / новый Runtime) используется **всеми** host-функциями (core/java/instance), а не только `PluginContentProviderProxy`. Шаг 3.4 плана шире, чем звучит: он затрагивает ~12 точек вызова. | Среднее | открыто — учтено в T-3.4 | T-3.4 |
| F-12 | Шаги 0.4 (A6/A7) выполнены частично: `PluginManifest::validate` / `RuntimeConfig::validate` **написаны**, но не вызываются нигде, кроме тестов; `api.check_compatibility` вызывается в `EnablePluginUseCase`, а `ForceEnablePluginUseCase` его сознательно обходит. `api.features` не проверяется. | Низкое | открыто — решается в T-0.4 | T-0.4 |
| F-13 | `run_command` уже частично изолирован: `plugin_command_to_host` резолвит `#`-пути и проверяет выход за пределы смонтированных директорий. Дыра — fallback на сырую строку для `program`, и полное отсутствие allowlist/таймаута/лимита вывода. `SerializableCommand` не имеет поля `env` — «env-изоляция» из шага 0.5 требует добавить поле или явно чистить окружение при запуске. | Среднее | частично закрыто решением Q7 (allowlist по директории Java ядра); остальное — в T-0.5 | T-0.5 |
