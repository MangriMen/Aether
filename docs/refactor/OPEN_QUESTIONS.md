## Q1. Что станет с importer/updater-путями packwiz? `РЕШЕНО: packwiz не переписывается в этом проходе (2026-09-20)`

packwiz сегодня подключён к ядру как `importers` + `updaters` (F-1), а не как content provider.
План 2.4.3 описывает его как провайдера с `resolve_install_plan`.

Варианты:
- **(a)** packwiz объявляет `contentProviders` и одновременно оставляет `importers`/`updaters`
  как тонкие обёртки, которые внутри зовут тот же `resolve_install_plan`.
- **(b)** importer/updater удаляются из packwiz, импорт пака идёт через обычную установку
  контента типа modpack; UI импорта и логика update-on-launch переписываются в ядре.

**Решение.** Ни (a), ни (b) прямо сейчас: packwiz остаётся importer/updater на jar-пути,
как есть. Миграция на `resolve_install_plan` откладывается до возобновления работы над
CurseForge / packwiz-native. Задачи `T-2.4.3.*` помечены **ОТЛОЖЕНО** (не `blocked`,
не `needs_decision`) и не входят в текущий проход.

Следствие: `run_command` и jar-путь остаются рабочими — это учтено в T-0.5 и T-1.5.B.

## Q2. Инвертировать порядок Фазы 1.5? `РЕШЕНО: да, T-1.5.A перед T-1.5.B (2026-09-20)`

План: 1.5.1 (`ro:`) → 1.5.2 (миграция packwiz). Это ломает packwiz между двумя коммитами (F-3).

**Решение.** Порядок инвертирован: сначала `T-1.5.A` (packwiz на `write_instance_file`),
затем `T-1.5.B` (`ro:` на `instances_dir`). Актуально независимо от Q1 и Q3: речь о
собственном WASI-коде плагина (`ensure_resource_in_instance_directory`,
`download_redistributable`), а не о jar-процессе, который работает вне WASM-песочницы.

Обе задачи — активные.

## Q3. CurseForge API-ключ и распространение файлов `РЕШЕНО: CurseForge отложен целиком (2026-09-20)`

`api.curseforge.com` требует `x-api-key`; отдельно — файлы с `allowFileDistribution: false`.

**Решение.** Работа над CurseForge-плагином откладывается полностью. `T-2.4.2.A/B/C` помечены

## Q4. Откуда берётся доверенный sha256 wasm-файла? `РЕШЕНО: TOFU при скачивании из GitHub (2026-09-20)`

Шаг 0.2 требует `Wasm::with_hash(sha256)`.

**Решение.** Trust On First Use: sha256 считается при скачивании плагина из GitHub-релиза
и сохраняется локально (в настройках / кэше капабилити плагина). При каждой загрузке —
сверка; несовпадение → **отказ в загрузке** с явным предупреждением.
Плагины, установленные не через GitHub-фетчер, по умолчанию не проверяются, но помечаются
в UI и в логе как **«плагин не верифицирован»**.

Разблокирует: T-0.2.

## Q10. Чем считать «Java, управляемую ядром» в allowlist `run_command`? `РЕШЕНО: вариант (d) — сверка с `java_versions` (2026-09-22)`

Q7 зафиксировал allowlist по директории: запуск разрешён, только если канонизированный путь
программы резолвится внутрь `location_info.java_dir()`. T-0.5 это реализовал. При реализации
вскрылось F-22: `get_java` отдаёт то, что лежит в `java_versions`, а туда `DiscoverJavaUseCase`
кладёт и системные установки. То есть ядро может выдать плагину путь, который его же allowlist
затем отвергнет, и обновление packwiz-пака сломается.

Варианты:
- **(a)** Оставить как есть (сравнение по `java_dir()`). Плюс: уже работает, fail-closed, нулевая
  сложность. Минус: у пользователя с системной Java нужной версии packwiz ломается, и причина
  неочевидна из ошибки.
- **(b)** Хранить в `java_versions` признак «установлена ядром» и пускать по нему, оставив
  канонизацию как дополнительную проверку. Плюс: allowlist совпадает с тем, что ядро реально
  выдаёт; переживает перенос каталога. Минус: миграция БД, нужен дефолт для существующих записей.
- **(c)** Не трогать allowlist, но чинить источник: `get_java` для плагинов отдаёт **только**
  core-managed Java, иначе ведёт себя как «не найдено» и плагин уходит в `install_java`.
  Плюс: расхождение исчезает в одном месте, allowlist не усложняется. Минус: ядро может второй раз
  скачать Java, которая у пользователя уже есть.

### Важный контекст для ответа (2026-09-22, F-23)
Allowlist проверяет только `program`. Аргументы плагин задаёт свободно, а `/cache` и `/instances`
смонтированы на запись, поэтому любая разрешённая Java запустит `-jar #/cache/<что угодно>`.
То есть **выбор между (a), (b), (c) и (d) на реальную защищённость не влияет** — ни один из них
не мешает вредоносному плагину выполнить свой код. Значит, решать стоит по UX и простоте кода,
а не по строгости. Ни один вариант при этом не расширяет права плагина: список Java формирует
ядро и пользователь (`install_java`, ручное добавление, `discover_java` по `JAVA_HOME`/`PATH`/`Program Files`/
каталогам лаунчеров), а host-функции, добавляющей запись в `java_versions`, плагину не выдано
(есть только `get_java` и `install_java`). Ни один из каталогов поиска не смонтирован плагину.

- **(d)** Сверять канонический путь `program` со списком путей из `java_versions` (то есть ровно с тем,
  что ядро само и выдаёт), оставив канонизацию. Плюс: **нет миграции БД и нет флага**, семантика
  точно совпадает с «ядро этот путь и выдало», работает и для системной, и для скачанной Java.
  Минус: `plugin_command_to_host` перестаёт быть чистой функцией от `LocationInfo` — список путей
  надо достать из storage в `handle_run_command` (он уже async) и прокинуть внутрь как `&[PathBuf]`.

**Решение (2026-09-22).** Вариант **(d)**. Разрешён запуск программы, чей канонизированный
путь лежит в `bin`-директории одной из Java, зарегистрированных в `java_versions` — то есть ровно
в том, что ядро и выдаёт через `get_java` / `install_java`. Системная Java разрешена наравне
со скачанной. Сравнение по `java_dir()` убрано.

Две детали, решённые при реализации:
- Сверка идёт с **директорией**, а не с точным файлом: `get_java` отдаёт `javaw`, а вызов `java`
  рядом с ним означает тот же runtime. Запись в `java_versions` хранит либо бинарник, либо саму
  `bin`-директорию — обе формы нормализуются к директории.
- Получилось **строже** прежнего правила по Q7: находиться где-то внутри `java_dir()` больше
  недостаточно. Пустой список `java_versions` запрещает всё (fail-closed), нерезолвящаяся
  запись отбрасывается и не расширяет allowlist.

Напоминание по F-23: на то, что вредоносный плагин может выполнить, это не влияет — выбор
сделан ради UX и простоты, а не ради строгости.

Разблокировало: T-0.5.A (реализовано 2026-09-22).

Примечание к Q7: формулировка «это закрывает A1» оказалась слишком сильной (F-23). Само решение Q7 не меняется и остаётся реализованным; речь только об ожиданиях от него.

## Q11. Что делать с механизмом генерации JSON-схем (`RegisterSchema` / `schema_sync`)? `РЕШЕНО: вариант (a) — восстановить (2026-09-22)`

Обнаружено при выполнении T-1.3 (см. F-27). `cargo test --workspace` падает на
`aether-core-gen`, тест `schema_sync::sync_all_schemas`, с сообщением `No schemas registered!`.

Установленные факты (проверены, не предположения):

- На этой ветке **нет ни одного `#[derive(RegisterSchema)]`**: `grep` по `packages/` и `apps/`
  находит только текст сообщения об ошибке внутри самого теста. Значит в inventory никто ничего
  не регистрирует, и `get_all_schemas()` пуст закономерно — это не тонкость линковки.
- Деривы есть только в коммите `fe4c1b94` ветки
  `fix/fix-instance-intall-stage-during-modpack-installing`, на трёх DTO (`capability.rs`,
  `plugin_capabilities.rs`, `plugin_manifest.rs`). Этот коммит **не предок HEAD**.
- Тест падал и **до** T-1.3 — проверено прогоном на чистом дереве через `git stash`.
- При этом инфраструктура закоммичена целиком: крейты `register-schema` и
  `register-schema-derive`, крейт `aether-core-gen` с тестом, и два файла
  `aether-core-plugin-api/src/v0/schemas/*.schema.json`.

**Почему это не просто «красный тест».** Два закоммиченных `.schema.json` — это публичная часть
контракта с плагинами, и сейчас их не проверяет ничто. Ближайшие задачи, которые меняют ровно
эти схемы: **T-1.4** (`api.hostFunctions` в манифесте) и **T-2.4.4** (`ProviderHandlers`).
То есть решать это дешевле **до** T-1.4, а не после.

Варианты:

- **(a) Восстановить механизм.** Вернуть `#[derive(RegisterSchema)]` + `#[schema_category(...)]`
  на типы, из которых схемы и генерировались (как минимум `PluginManifestDto`,
  `PluginCapabilitiesDto`, `CapabilityDto`), прогнать `UPDATE_SCHEMAS=1`, зафиксировать
  результат. Плюс: схемы снова верифицируются, T-1.4 и T-2.4.4 получают защиту от
  рассинхрона. Минус: надо решить, какие ещё типы регистрировать, и принять возможный
  большой диff в `.schema.json`, если они успели устареть.
- **(b) Удалить механизм.** Выкинуть `register-schema`, `register-schema-derive`,
  `aether-core-gen` и оба `.schema.json`. Плюс: минус три крейта и красный тест, ничего
  не «делает вид», что работает. Минус: у плагинов и редакторов пропадает JSON Schema для
  манифеста; по Q5 контракт и так ломается в T-1.4 — без схемы это станет менее заметно.
- **(c) Оставить как есть, но перестать врать.** Пометить тест `#[ignore]` с внятной причиной,
  схемы оставить как справочные, решение отложить. Плюс: `cargo test --workspace` становится
  зелёным, ноль риска. Минус: долг остаётся, и в T-1.4 схему всё равно придётся править руками.

Рекомендация исполнителя: **(a)**, и до T-1.4 — механизм уже оплачен (крейты написаны и
закоммичены), а T-1.4 и T-2.4.4 меняют ровно те схемы, которые он и сторожит. Но выбор между
«чинить» и «выкинуть» — про то, нужна ли вам JSON Schema манифеста снаружи, и это ваше решение.

**Решение (2026-09-22).** Вариант **(a)** — восстановить. Обоснование владельца: схемы нужны
для удобства разработчиков плагинов (проверка манифеста при написании) и, отдельно, для тех,
кто пишет плагин **не на Rust** и не может импортировать DTO напрямую.

Детали, выясненные и решённые при реализации (T-3.6):

- `JsonSchema` **уже висел** на всех нужных типах — не хватало только `RegisterSchema`.
- Публикуются **два корневых типа**: `PluginManifestDto` и `PluginCapabilitiesDto`. Больше
  не нужно: `schema_for!` инлайнит вложенные типы в `$defs` корневой схемы, и плагинный автор
  валидирует ровно два файла — `manifest.json` и `capabilities.json`. На ветке `fe4c1b94`
  генерировалось 14 файлов, из них 12 были не нужны.
- **`Dto` не протекает в публичный контракт.** В `register-schema-derive` возвращена поддержка
  `#[schema_name("...")]` (она была на `fe4c1b94`, на HEAD отсутствовала), а на типы добавлен
  `#[schemars(rename = "...")]`. Имена файлов, `title` и ключи `$defs` остались прежними:
  `PluginManifest`, `RuntimeConfig`, `ProviderHandlers` и т.д. `Dto` — внутреннее соглашение
  Rust, во внешнем контракте ему не место.
- Пояснения о том, как схема публикуется, оставлены **обычными `//` комментариями**, а не
  doc-комментариями: `schemars` кладёт doc-комментарий в `description`, который читает автор
  плагина, и внутренние заметки туда попадать не должны.

Разблокировало: T-3.6 (выполнена 2026-09-22).

## Q12. Пересматривать ли отказ от `PackManager` в пользу `InstallPlan`? `РЕШЕНО: вариант (a) — не пересматривать; (c) отложен к рассмотрению в T-2.2 (2026-09-22)`

На ветке `fix/fix-instance-intall-stage-during-modpack-installing` (коммиты `fe4c1b94`,
`fb9f7286`; 124 файла, +2780/−1871) лежит **рабочая** альтернативная архитектура: порты
`Importer`/`Updater` удалены, вместо них единый трейт `PackManager`
(`resolve_pack_metadata` / `install` / `update` / `check_updates`), модели `PackSource`,
`PackMetadata`, `UpdateStatus` и реализация для Modrinth.

`refactoring_plan.md` эту концепцию **уже отверг** — строки 4, 7 и 169: «packManagers
отбрасывается как отдельная концепция», «`InstallTarget::Existing | New` покрывает разницу
между install и update», «избыточен». Забрать предполагалось только `resolve_pack_metadata`
(строка 8) — оно и так уже расписано в T-2.1.B, T-2.2 и T-2.4.1.

Вопрос возник потому, что ветка существует в рабочем виде, и стоит явно подтвердить отказ,
а не обходить его молчанием.

### Чем отличаются по существу

Главное различие — **кто решает, какие файлы окажутся в инстансе**.

- `InstallPlan` (план): плагин **описывает** план, ядро его исполняет. Ядро видит полный список
  файлов с хешами до того, как что-то записано.
- `PackManager` (ветка): провайдер **сам** скачивает и раскладывает файлы. В доке трейта прямо:
  *«The manager should download/extract all pack files into the instance directory»*.

### Плюсы возврата к `PackManager`

- **Код уже написан и работает**, включая Modrinth-реализацию. Фаза 2 — самая большая
  в текущем плане (9 активных задач), и часть её отпала бы.
- **Снимает двойственность importer/updater** (F-1) уже сейчас. В текущем плане это отложено
  до T-2.4.3.D, а она `ОТЛОЖЕНО` по Q1 — то есть в этом проходе F-1 не чинится вообще.
- **`check_updates` как явный дешёвый вызов** с типом `UpdateStatus`. В плане проверка
  обновлений выражается через `resolve_pack_metadata` + сравнение, что менее явно.

### Минусы возврата — и почему они перевешивают

- **Конфликтует с уже сделанной работой по безопасности.** T-1.3 только что сделала
  `write_instance_file` единственным аудируемым путём записи, T-1.5.B закроет `instances_dir`
  на `ro:`. При `PackManager` ядро видит отдельные записи, но **не видит списка файлов заранее**
  и не может проверить его централизованно. Это не делает `ro:` невозможным, но обесценивает его
  смысл: решение «что положить» остаётся внутри плагина.
- **Теряется диффинг install/update.** В плане это одна и та же дорога: executor сравнивает план
  с `PackStorage` и качает только дельту (T-2.3.B). У `PackManager` `update` делегирован
  провайдеру — каждый реализует свою логику, ядро дельту посчитать не может.
- **Нет замены `ProviderRef`.** Механизм, которым packwiz ссылается на контент CurseForge без
  вызова плагин→плагин, существует только в `InstallPlan` (`ContentSource::ProviderRef` +
  `resolve_file`). У `PackManager` packwiz пришлось бы тащить собственный клиент CurseForge —
  это прямо противоречит требованию Q3 «добавление CF позже не требует рефакторинга трейта».
- **Ветка отстала**: точка расхождения — 2026-07-16, с тех пор в HEAD легли T-0.1…T-0.6, T-0.5.A,
  T-1.3, T-3.6. Мерж не бесплатный, он затронет ровно те файлы, что менял рефакторинг.

### Варианты

- **(a) Не пересматривать.** План остаётся, ветка не мержится. Из неё уже забрано всё ценное:
  механизм схем (T-3.6) и багфикс стадии установки (T-F.1). Ветку можно удалить или оставить
  как исторический контекст.
- **(b) Пересмотреть — принять `PackManager` вместо `InstallPlan`.** Требует переписать
  Фазу 2 целиком и заново решить Q3 (как CurseForge встроится без `ProviderRef`).
- **(c) Гибрид: оставить `InstallPlan`, но забрать из ветки `UpdateStatus` / явный
  `check_updates`** как отдельный дешёвый вызов рядом с `resolve_pack_metadata`. Не трогает
  контракт установки, добавляет только понятный ответ на «есть ли обновление».

**Рекомендация исполнителя: (a)**, и отдельно рассмотреть (c) в рамках T-2.2 — там всё равно
проектируется трейт, и явный `check_updates` туда ложится без конфликта. Вариант (b) стоит
выбирать, только если приоритет — быстро закрыть F-1 и вы готовы отказаться от `ProviderRef`,
то есть фактически от плана интеграции CurseForge по Q3.

**Решение (2026-09-22).** Вариант **(a)** — отказ от `PackManager` подтверждён, план остаётся
без изменений. Вариант **(b) отклонён явно**: `InstallPlan` и `ProviderRef` сохраняются, Фаза 2
стартует как спроектирована.

Вариант **(c) не отклонён, а отложен**: забрать из ветки `UpdateStatus` / явный `check_updates`
как отдельный дешёвый вызов — **рассмотреть при выполнении T-2.2**, где всё равно проектируется
трейт `ContentProvider`. Это рассмотрение, а не обязательство: T-2.2 вправе решить, что
`resolve_pack_metadata` покрывает потребность, и не добавлять `check_updates`. Записано
в карточку T-2.2 разделом «Отложенное из Q12 (c)».

Судьба самой ветки `fix/fix-instance-intall-stage-during-modpack-installing`: всё ценное из неё
изъято — механизм схем (T-3.6, выполнено) и багфикс стадии установки (T-F.1, заведена).
Мержить её не нужно; удалять или оставить как исторический контекст — на усмотрение владельца.

Разблокировало: ничего (Фаза 2 и так не была заблокирована).
