## Что сделать
Новый исполнитель плана в app-слое инстанса:
- `InstallTarget::New(spec)` → создать инстанс через существующий use case создания;
  `Existing { instance_id }` → взять как есть;
- `resolve_all_refs(files, depth_limit = 3)`: каждый `ContentSource::ProviderRef` резолвится
  вызовом `resolve_file` у провайдера из реестра; циклы и превышение глубины → ошибка;
- скачивание + верификация хеша + запись файла (через существующий `ContentFileService`);
- сам диффинг — в T-2.3.B, overrides — в T-2.3.C, прогресс — в T-2.3.D (здесь оставить
  явные точки расширения, а не заглушки-`todo!()`).

### Замечание по Q3 (2026-09-20)
Резолв `ContentSource::ProviderRef` реализуется **сейчас**, несмотря на то что второго
провайдера (CurseForge) в этом проходе не будет. Проверяется мок-провайдером в тестах.
Цель — чтобы появление CF позже не потребовало менять executor.

## Файлы
- `features/instance/app/use_cases/content_provider/` — новый модуль `install_plan_executor.rs`
- `features/instance/app/ports/use_case_ports.rs`, `features/instance/app/di.rs`,
  `core/app/di.rs` — регистрация

## Как проверить
- `cargo test -p aether-core` + тесты с мок-провайдером: `ProviderRef` → `Direct`; цепочка
  глубже 3 → ошибка; ссылка на неизвестного провайдера → `ContentProviderNotFound`.
- Ручной сценарий отложен до T-2.5 (пока executor не подключён к команде установки).

## Ловушки
- Резолв ссылок не должен идти плагин→плагин: только ядро вызывает `resolve_file` второго
  провайдера (это зафиксированное решение плана, не пересматривать).
- Параллельное скачивание ограничено общим семафором `FetchSemaphore` — не заводить свой.
