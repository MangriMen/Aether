## Что сделать
Собственная host-функция `http_get(request) -> HttpResponse`:
- отдельный `reqwest::Client` с `redirect::Policy::none()` (общий клиент приложения следует
  редиректам — F-9);
- проверка хоста **в хосте** по `allowed_hosts` плагина (манифест + настройки), а не только
  внутри Extism;
- запрет приватных/loopback/link-local адресов (в т.ч. `169.254.169.254`) — резолвить имя
  и проверять все полученные IP;
- лимит размера ответа и таймаут;
- DTO запроса/ответа — в `aether-core-plugin-api` (`v0`), рядом с существующими DTO.

Встроенный `http_request` Extism остаётся как fallback — задокументировать риск редиректов
в README плагинного API.

## Как проверить
- `cargo test -p aether-core`: unit-тесты матчинга `allowed_hosts` (включая wildcard-формы,
  которые поддерживает Extism) и отсечения приватных IP.
- Интеграционный тест на локальном http-сервере: ответ 302 на другой хост → ошибка, а не переход.
- Ручной сценарий: плагин, вызывающий `http_get` к разрешённому хосту, получает тело ответ.

## Ловушки
- `PluginContext` сейчас не хранит манифест — нужно пробросить allowed_hosts при создании
  контекста в `get_host_functions` (подпись меняется, затрагивает все host-функции).
- DNS rebinding: проверять IP **после** резолва и использовать тот же резолв для запроса
  (или хотя бы задокументировать остаточный риск).
- Запрос идёт из синхронного контекста Extism — пока через `execute_async`; не чинить это здесь,
  это задача T-3.4.
