## Что сделать
Две host-функции:
- `write_instance_file(instance_id, relative_path, bytes)` — единственный способ записи в инстанс;
- `read_instance_file(instance_id, relative_path) -> bytes`.

Требования: `relative_path` всегда относительный, без `..`, без абсолютных префиксов и без
symlink-выхода за корень инстанса (канонизировать и сравнить с корнем — как уже делает
`plugin_path_to_host`); лимит размера; проверка, что инстанс существует.

## Файлы
- `features/plugins/infra/extism/host_functions/features/instance.rs`
- `features/plugins/infra/extism/host_functions/get_host_functions.rs`
- `aether-core-plugin-api/src/v0/dto/instance/` — DTO параметров
- переиспользовать `InstanceFileService` / `ContentFileService` из `features/instance/app/ports`

## Как проверить
- `cargo test -p aether-core`: `../` в пути, абсолютный путь, symlink наружу — все отклоняются.
- Ручной сценарий: временный тестовый вызов из packwiz (или unit-тест на хост-функции),
  файл появляется внутри директории инстанса.

## Ловушки
- Пути от плагина приходят в WASI-форме (`/instances/...`, `/mnt/d/...` на Windows) —
  для этих функций принимать **только** `instance_id` + относительный путь, не WASI-путь.
- Запись должна идти через тот же слой, что и остальная запись в инстанс, иначе состояние
  `PackStorage` разъедется с диском.

## Что получилось (для ревью)

Слои — снизу вверх:

1. `features/instance/infra/services/instance_relative_path.rs` — **вся проверка пути**.
   `validate_relative_path` работает по сырой строке (а не через `std::path`), потому что путь
   от плагина — не путь этого хоста: на Linux `mods\..\..\evil` был бы одним `Normal`-сегментом.
   Обе разделительные черты (`/` и `\`) трактуются одинаково на всех платформах.
   Отвергаются: пустой путь, NUL, абсолютные формы (`/…`, `\…`, `C:\…`, `\\server\share`,
   `\\?\C:`), сегменты `.` и `..`, пустые сегменты (двойной или хвостовой разделитель),
   `:` внутри сегмента (буква диска и Windows ADS `file.txt:secret`).
   `resolve_instance_file_path` затем канонизирует **самого глубокого существующего предка**
   кандидата (через `symlink_metadata`, чтобы висячая ссылка не считалась «ещё не существует»)
   и требует, чтобы результат остался под каноническим корнем инстанса — это и ловит symlink.
   Две проверки не заменяют друг друга: `mods/x` проходит строковую и падает на symlink-овой.
2. `InstanceFileService::write_instance_file` / `read_instance_file` — единственный путь записи.
   Запись: лимит → резолв → `create_dir_all` → **повторный резолв** (на случай подмены компонента
   симлинком между проверкой и записью) → запись. Чтение: резолв → `metadata` → отказ, если это
   не обычный файл → лимит по `metadata.len()` (файл сверх лимита не читается в память вообще).
3. Host-функции `write_instance_file` / `read_instance_file` принимают `instance_id` +
   относительный путь и **никогда** WASI-путь. Перед обращением к сервису — `require_instance`
   через `GetInstanceUseCasePort`: неизвестный id отвергается, директория под него не создаётся.
   Логика вынесена в `write_instance_file_with` / `read_instance_file_with`, которые берут два
   порта вместо всего `AetherContainer` — именно ради unit-теста из раздела «Как проверить».

Принятые решения, которые стоит подтвердить на ревью:

- **Лимит 64 MiB** (`MAX_INSTANCE_FILE_BYTES`). Обоснование: байты всё равно проходят через
  линейную память плагина (дефолт 256 MiB по Q8), больший лимит плагину нечем использовать.
  Следствие записано в **F-25**: крупный контент должен идти через `download_to_cache` (T-1.2),
  а не через эту функцию. Если при T-1.5.A окажется, что packwiz копирует что-то крупнее —
  лимит придётся пересматривать вместе с T-1.2.
- **Сверка с директорией, а не с точным файлом** тут не применяется: в отличие от allowlist
  `run_command`, здесь сравнение строгое — путь обязан лежать под корнем инстанса.
- Три новых варианта `InstanceError` потребовали правки `InstanceErrorDto` десктопа и
  регенерации TS-биндингов; `size`/`limit` там переданы строками, потому что specta запрещает
  экспорт `u64` (см. **F-26**).

Заведено на будущее (в `FINDINGS.md`, не в этой задаче):
- **F-24** — `write_instance_file` не обновляет `PackStorage`; связь «файл ↔ пак» держится
  на `InstanceWatcherServiceImpl`, который следит только за контент-папками. Не регрессия
  (packwiz и сейчас пишет мимо `PackStorage` через `std::fs::copy`), но ловушка карточки
  закрыта лишь в той мере, в какой её закрывает watcher. Учитывать в T-1.5.A и T-2.3.B.
- **F-25** — лимит 64 MiB и его следствие для крупного контента (T-1.2, T-1.5.A).
- **F-26** — любое расширение `InstanceError` требует правки DTO десктопа + биндингов.
- **F-27** — `schema_sync::sync_all_schemas` в `aether-core-gen` падал и до этой задачи
  (проверено прогоном на чистом дереве); к T-1.3 отношения не имеет.
