## Что сделать
- Расширить `ProviderHandlers`/`ProviderHandlersDto` полями `resolveFile`,
  `resolveInstallPlan`, `resolvePackMetadata`; `installAtomic` сделать опциональным
  (удаляется в T-3.1).
- Пересмотреть флаги `supportsInstallAtomic`/`supportsInstallModpacks` в
  `ContentProviderCapabilityMetadataDto` (F-8): заменить на набор, отражающий новый контракт,
  либо выводить из наличия обработчиков.
- Прокинуть новые методы в `PluginContentProviderProxy` через Msgpack; DTO плана установки —
  в `aether-core-plugin-api/v0`.

### Решения по Q5 и Q3 (2026-09-20)
- Источник `aether-core-plugin-api` — `MangriMen/aether-core`, плагины пинятся на тег (Q5).
- В этом проходе новый контракт реально использует только встроенный Modrinth: plugin-side
  потребителей (packwiz-native, CurseForge) нет — они отложены. Задача всё равно активна,
  потому что контракт обязан быть готов до их появления, без повторного рефакторинга.
- Из плагинов в этом проходе пересобирается только packwiz (его `capabilities.json` остаётся
  importer/updater — новые поля провайдера ему не нужны).

## Как проверить
- `cargo test -p aether-core` + `cargo check` всего воркспейса.
- Тест маппинга: `capabilities.json` нового формата → доменная модель → прокси вызывает
  правильные имена функций.
- Ручной сценарий: плагин, реализующий только `resolve_*`, регистрируется как провайдер.

## Ловушки
- Ломает `capabilities.json` обоих плагинов — выкат по порядку из Q5.
- `function_exists` в Extism проверяет только сигнатуру (0 параметров, 0/1 i32), то есть
  «обработчик есть» ≠ «обработчик правильный»; ошибку несоответствия ловить на уровне Msgpack.
