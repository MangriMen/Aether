## Проблема
Allowlist `run_command`, принятый по Q7 и реализованный в T-0.5, разрешает запуск только если
канонизированный путь программы лежит внутри `location_info.java_dir()`. Но `get_java` отдаёт
то, что лежит в таблице `java_versions`, а туда `DiscoverJavaUseCase` кладёт **и системные
установки** (`features/java/infra/discovery_paths.rs`). Получается расхождение: ядро само выдало
плагину путь, а потом само же отказалось его запускать.

Симптом: у пользователя в БД для нужной мажорной версии — системная Java (например,
`C:\Program Files\Java\...`), packwiz получает её из `get_java(8)` и падает на `run_command`
с `AccessViolation`. Обновление пака ломается.

На машине владельца на 2026-09-21 риска нет: в `java_versions` только пути внутри `cache/java`,
Java 8 не зарегистрирована вообще, поэтому packwiz уходит в `install_java(8)` → `java_dir()`.
Это везение конкретной установки, а не свойство кода.

## Как проверить
- Тест: Java, помеченная как обнаруженная вне ядра, не проходит allowlist.
- Тест: Java, установленная ядром, проходит — в том числе если её каталог перенесён.
- Ручной сценарий: обновление packwiz-пака на инстансе, где активна системная Java.

## Ловушки
- Миграция БД: у существующих записей флага нет, нужен разумный дефолт (скорее всего
  «не управляется ядром», то есть fail-closed) плюс проставление флага при `install_java`.
- Симлинки и перенос каталога: флаг в БД не защищает от подмены файла по пути, проверку
  канонизации убирать нельзя — она должна остаться поверх флага, а не вместо него.
