## Что сделать
- Считать sha256 wasm-файла при скачивании плагина из GitHub-релиза и сохранить эталон
  (место хранения — по решению Q4).
- При загрузке плагина передавать `Wasm::file(path).with_hash(sha256)`.
- Для локально установленных плагинов — поведение по решению Q4 (хеш опционален).
- Добавить в ядро sha256 (крейт `sha2`; сейчас есть только `sha1_smol`, см. F-6 и Q6 —
  согласовать выбор крейта с T-1.2 / T-2.1.A).

### Решение по Q4 (2026-09-20) — TOFU
- sha256 считается при скачивании плагина из GitHub-релиза и сохраняется локально
  (настройки / кэш капабилити плагина).
- При каждой загрузке — сверка; несовпадение → **отказ в загрузке** с явным предупреждением.
- Плагины, установленные не через GitHub-фетчер, по умолчанию не проверяются, но помечаются
  в UI и в логе как **«плагин не верифицирован»**.
- Хеш-функции берём из общего набора по Q6 (`sha2`, см. T-2.1.A).

## Файлы
- `features/plugins/infra/github_plugin/fetcher.rs`, `provider.rs`
- `features/plugins/infra/fs_plugin_storage/storage.rs` (если эталон хранится рядом с плагином)
- `features/plugins/infra/extism/extism_plugin_loader.rs` (`build_wasm_manifest`)
- `shared/hash/infra/mod.rs`

## Как проверить
- `cargo test -p aether-core` + новый тест: подменённый wasm-файл → `PluginError::LoadFailed`.
- Ручной сценарий: установить плагин из GitHub-релиза, затем дописать байт в `.wasm` —
  включение плагина должно падать с внятной ошибкой.

## Ловушки
- `with_hash` — метод `Wasm`, не `Manifest` и не `PluginBuilder`.
- Кеш компиляции (`with_cache_config`) не должен «спасать» подменённый файл — проверить, что
  ошибка возникает до использования кеша.

## Что получилось (2026-09-21)

Схема доверия:

1. `record_plugin_verification` (`features/plugins/app/record_plugin_verification.rs`)
   считает sha256 установленного `.wasm` и пишет `verification.json` в директорию плагина.
   Вызывается в двух точках, где байты только что приехали от провайдера:
   `install_plugin_from_provider` (tauri-команда) и `UpdatePluginUseCase::execute`.
2. `ExtismPluginLoader::resolve_expected_wasm_sha256` при каждой загрузке перечитывает
   файл и сверяет с эталоном: несовпадение → `PluginError::LoadFailed` с текстом, из
   которого видно оба хеша и что плагин надо переустановить.
3. Тот же хеш уезжает в `Wasm::file(path).with_hash(sha256)` — двойная проверка закрывает
   окно между нашим чтением файла и чтением Extism.
4. Нет эталона (плагин поставлен из локального архива) → загрузка разрешена,
   `tracing::warn!` «plugin is not verified». Уже установленные до этой задачи плагины
   попадают именно сюда, поэтому ничего не ломается.

Эталон живёт рядом с плагином и умирает вместе с его директорией: `PluginStorage::remove`
и remove-then-add при обновлении стирают его, так что переустановка всегда заново
устанавливает доверие по свежескачанным байтам, а не сверяется с протухшим хешем.
