## Что сделать
Ввести в домен инстанса типы ровно по листингу плана 2.1: `InstallPlan`, `InstallTarget`,
`InstallFileEntry`, `ContentSource`, `FileHash`, `OverrideSource`. Без логики — только модель
и конверсии, которые уже нужны (`FileHash` ↔ строка+формат).

`NewInstanceSpec` — использовать существующий доменный тип создания инстанса, а не вводить
дубликат (проверить `NewInstanceDto`/соответствующий доменный аналог).

### Решение по Q6 (2026-09-20)
`FileHash { Sha1, Sha256, Sha512 }` (в план входил только Sha1/Sha512). Md5 не добавляем —
отложен вместе с CurseForge. В ядро добавляется крейт `sha2`.

### Требование расширяемости под CurseForge (Q3)
CurseForge-плагин в этом проходе не пишется, но `ContentSource::ProviderRef` и вся модель
обязаны быть спроектированы так, чтобы его добавление позже **не требовало повторного
рефакторинга модели и трейта**. Формат `provider_id`/`content_id`/`version` в `ProviderRef`
зафиксировать здесь явно и сослаться на него из T-2.2 и T-2.3.A.

## Файлы
- `features/instance/domain/model/` — новый модуль `install_plan.rs` (+ `mod.rs`)
- `features/instance/domain/model/pack.rs` — сверить с `PackFileDownload`/`PackFileOption`,
  не дублировать смысл

## Как проверить
- `cargo check -p aether-core`, `cargo clippy -p aether-core -- -D warnings`.
- Юнит-тесты на разбор/сериализацию `FileHash` и `ContentSource`.

## Ловушки
- Не заводить второй словарь терминов: в коде уже есть `PackFile`, `ContentFile`,
  `DownloadedContent` (F-5). В карточке T-2.3.B зафиксировано, как они соотносятся.
- `relative_path` в `InstallFileEntry` — всегда слэш-нормализованный относительный путь
  (в проекте для этого используется `path_slash`).
