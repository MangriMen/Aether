# T-3.3 — Разделить `PluginError` и `PluginProviderError`

| Ревью перед мержем | нет |

## Что сделать
Разнести смешанные контексты: жизненный цикл и исполнение плагина (`LoadFailed`,
`FunctionCallFailed`, `AccessViolation`, `AlreadyLoaded`, …) остаются в `PluginError`;
всё про получение плагина из источника (`ProviderFetchError`, `ProviderRateLimited`,
`ManifestNotFound`, `ExtractionFailed`, …) уезжает в новый `PluginProviderError`
с конверсией на границе.

## Файлы
- `features/plugins/domain/models/plugin_error.rs`
- `features/plugins/infra/github_plugin/*`, `infra/zip_plugin_extractor/*`,
  `infra/fs_plugin_source_storage/*`
- `aether-core-plugin-api/src/v0/dto/host_error/plugin_error.rs` — если ошибки уходят в плагин

## Как проверить
- `cargo check` воркспейса, `cargo test -p aether-core`, clippy без предупреждений.
- Фронт: сообщения об ошибках установки плагина не деградируют (проверить i18n-ключи).

## Ловушки
- Ошибки маппятся в DTO для фронта — изменение формы enum ломает биндинги, нужна перегенерация.

## Проверка перед мержем (компенсация уровня модели)
Модель — Sonnet, поэтому обязательны:
1. `cargo check` воркспейса + перегенерация биндингов, если DTO ошибок изменились.
2. Проверить, что сообщения об ошибках установки плагина в UI не потеряли i18n-ключи.
