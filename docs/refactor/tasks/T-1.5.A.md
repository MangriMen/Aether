## Перед стартом: как получить новые DTO (решено 2026-09-22)

**Это первое, обо что упирается задача.** `packwiz/Cargo.toml` тянет plugin-api с GitHub:

```toml
aether-core-plugin-api = { git = "https://github.com/MangriMen/aether.git", version = "0.2.0" }
```

`WriteInstanceFileParamsDto` / `ReadInstanceFileParamsDto` добавлены в T-1.3 (коммит `cdc8ebfc`),
который **существует только локально и не запушен**. То есть `cargo build` новых DTO не увидит,
и задача встанет на первой же сборке.

**Решение владельца: работать через локальный path-override, а не выпускать тег.**
В **корневой** `Cargo.toml` репозитория `packwiz-plugin` (патчи применяются только из корня
workspace) добавить:

```toml
[patch."https://github.com/MangriMen/aether.git"]
aether-core-plugin-api = { path = "../aether/packages/core/aether-core-plugin-api" }
```

Путь верен, если `aether` и `packwiz-plugin` лежат рядом (как сейчас, в `Z:\Projects\git\`).
Версии совпадают: локальный крейт — `0.2.0`, зависимость требует `0.2.0`, иначе `[patch]` молча
не применится.

**Почему оверрайд, а не тег.** T-1.3 помечена «Ревью перед мержем: да», а тег — это уже
публикация контракта наружу (Q5). Если на ревью форма DTO изменится, тег окажется выпущен зря,
а packwiz придётся переделывать. Выкат по Q5 (ядро → тег `aether-core-plugin-api` → плагины)
делается **после** ревью T-1.3.

**Чего нельзя делать:**
- **Не коммить `[patch]`** — в репозитории есть CI, а на его машине каталога `../aether`
  не существует, сборка упадёт. Патч живёт только в рабочем дереве.
- **Не коммить изменения `Cargo.lock`**, вызванные патчем, по той же причине.
- Из-за этого задачу **нельзя закрыть в `done` полностью**: её финальное состояние требует
  реального пина по Q5. Закрывать в `done` только код плагина, а состояние зависимости
  отметить в «Осталось» и завести на выкат отдельный пункт, если он к тому моменту не сделан.

Побочно замечено (на эту задачу не влияет): пин идёт на `MangriMen/aether.git` и по версии,
а Q5 зафиксировал канонический `MangriMen/aether-core` и пины **на теги**. Это известная
**F-7**, чинится в T-1.4 — здесь не трогать.

## Как проверить
- `cargo build --target wasm32-unknown-unknown` (или через `xtask build`) в репозитории плагина.
  Сборка идёт с `[patch]` из раздела «Перед стартом» — собранный `.wasm` от этого полноценен,
  ручной сценарий ниже на нём выполняется как есть.
- Ручной сценарий (обязателен): собрать плагин, установить в aether, импортировать packwiz-пак,
  затем обновить его — `packwiz-installer.jar` появляется в директории инстанса.

## Ловушки
- После этой задачи плагин требует ядро с T-1.3 — зафиксировать минимальную `apiVersion`.
- Ядро с T-1.3 должно быть **собрано из этой же ветки** (`ref/refactor-content-installing`),
  иначе host-функций `write_instance_file` / `read_instance_file` в нём просто нет и плагин
  упадёт в рантайме, а не на сборке.
- Лимит `write_instance_file` — **64 MiB** (F-25). Для `packwiz-installer.jar` с запасом хватает,
  но если плагин начнёт класть в инстанс что-то крупное, упрётся в него; крупное должно идти
  через `download_to_cache` (T-1.2).
- `write_instance_file` **не обновляет `PackStorage`** (F-24): связь «файл на диске ↔ запись
  в паке» держится на `InstanceWatcherServiceImpl`, который следит только за контент-папками.
  Проверить, что записываемые пути попадают туда, либо явно зафиксировать, что не попадают.
- `instance_get_dir` возвращает путь в плагинном пространстве; для `write_instance_file` нужен
  `instance_id` + относительный путь, а не этот путь.

## Проверка перед мержем (компенсация уровня модели)
Модель — Sonnet, поэтому обязательны:
1. Сборка плагина через `xtask` и установка в aether.
2. Ручной сценарий: импорт пака и его обновление — `packwiz-installer.jar` появляется в инстансе.
3. Проверить, что в плагине не осталось `std::fs::copy`/`write` в директорию инстанса (grep).
