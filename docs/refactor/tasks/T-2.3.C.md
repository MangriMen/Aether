## Что сделать
`extract_overrides(instance_id, OverrideSource)`:
- `Archive { archive_path, subdir }` — распаковка только указанного подкаталога, с проверкой
  `enclosed_name()` (тот же класс уязвимости, что T-0.3);
- `Directory { path }` — рекурсивное копирование с той же проверкой выхода за корень.
Переиспользовать существующий код распаковки модпаков Modrinth, если он уже это делает.

## Файлы
- `features/instance/app/use_cases/content_provider/install_plan_executor.rs`
- `shared/archive/` — если распаковка живёт там
- `features/instance/infra/content_providers/modrinth/content_provider/modrinth_content_provider.rs`
  (`deploy_modpack_files` — как образец существующего поведения)

## Как проверить
- `cargo test -p aether-core`: архив с записью `../evil` → ошибка; обычные overrides
  раскладываются по инстансу.

## Ловушки
- Overrides не должны затирать файлы, уже записанные по плану (порядок применения зафиксировать).
- Пути внутри архива — с прямыми слэшами независимо от ОС.

## Проверка перед мержем (компенсация уровня модели)
Модель — Sonnet при наличии zip-slip-риска, поэтому обязательны:
1. Тест: архив с записью `../evil` отклоняется (как в T-0.3).
2. Тест: порядок применения overrides относительно файлов плана зафиксирован тестом.
