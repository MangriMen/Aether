## Что сделать
Реализовать в `ModrinthContentProvider`:
- `resolve_file` — по `content_id` + версии + game_version + loader вернуть `ResolvedFile`
  (переиспользовать `resolve_project_version` / `get_project_version_for_game_version`);
- `resolve_install_plan` — и для одиночного мода, и для `.mrpack` (файлы + overrides из архива);
- `resolve_pack_metadata` — по решению Q9.
`install_atomic`/`install_modpack` пока не удалять — они уходят в T-3.1.

### Решение по Q9 (2026-09-20)
Modrinth **реализует** `resolve_pack_metadata` для `.mrpack`, оборачивая существующие
`resolve_modpack_version` / `perform_modpack_import`. Вариант с `UnsupportedOperation` отклонён.

## Как проверить
- `cargo test -p aether-core` (существующие тесты Modrinth должны продолжать проходить).
- Ручной сценарий (после T-2.5): установка одиночного мода с Modrinth в существующий инстанс
  и установка `.mrpack` в новый инстанс; повторная установка того же мода не дублирует файл.

## Ловушки
- Скачивание в `resolve_*` делать нельзя: метод только резолвит, скачивает executor.
  Исключение — сам файл `.mrpack`, без которого не получить список файлов; тогда он скачивается
  в кеш, а в план кладутся уже разобранные записи и `OverrideSource::Archive`.
- Modrinth отдаёт sha1 и sha512 — проверить соответствие с вариантами `FileHash` (Q6).
