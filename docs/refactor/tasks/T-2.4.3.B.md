## Что сделать
- `resolve_install_plan`: из разобранного пака построить `InstallPlan`:
  записи с прямым `download.url` → `ContentSource::Direct { url, hash }`;
  записи CurseForge → `ContentSource::ProviderRef { provider_id: "curseforge", content_id, version }`
  в формате, зафиксированном в T-2.4.2.C;
  `InstallTarget::New` при импорте пака, `Existing` при обновлении;
  нефайловые ресурсы пака (config и т.п. из индекса) — как обычные файлы плана.
- `resolve_file`: для одиночного файла пака (нужен, если пак сам станет источником ссылок).

## Файлы
- `packwiz/src/features/instance/app/*` (новые обработчики вместо `import`/`update`-логики)
- `packwiz/src/lib.rs`, `packwiz/capabilities.json`

## Как проверить
- `cargo test -p packwiz`: тест на паке с обоими типами записей → в плане есть и `Direct`,
  и `ProviderRef`.
- Ручной сценарий: импорт реального packwiz-пака с CF-записями в новый инстанс, все файлы
  на месте, jar не использовался.

## Ловушки
- `provider_id` — это `ProviderId { plugin_id, capability_id }` (строковая форма
  `plugin#capability`), а не просто `"curseforge"`; захардкоженный `plugin_id` чужого плагина —
  плохая идея, обсудить формат ссылки при ревью.
- Опциональные файлы пака (`option.optional`) должны попадать в план с `optional: true`,
  а не отбрасываться.
