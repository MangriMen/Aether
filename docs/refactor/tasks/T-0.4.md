# T-0.4 — Вызов `manifest.validate()` при включении плагина

| Поле | Значение |
| --- | --- |
| Статус | blocked |
| Шаг плана | Фаза 0, шаг 0.4 (A6, A7) |
| Репозиторий | aether |
| Зависит от | — |
| Модель | Claude Sonnet 5 |
| Ревью перед мержем | нет |

## Что сделать
- Вызывать `PluginManifest::validate(&PLUGIN_API_VERSION)` в `EnablePluginUseCase::execute`
  до загрузки плагина; ошибку маппить в состояние `PluginState::Incompatible`/`Failed`
  с внятной причиной.
- В `ForceEnablePluginUseCase` обходить **только** проверку версии API, но **не**
  `RuntimeConfig::validate()` (запрет абсолютных `allowed_paths` должен действовать всегда).
- `api.features` пока не реализуем: если список непустой — писать предупреждение в лог
  (полноценная проверка — отдельная задача после T-1.4).

## Файлы
- `features/plugins/app/enable_plugin.rs`
- `features/plugins/app/force_enable_plugin.rs`
- `features/plugins/domain/models/plugin_manifest.rs` (если нужно разделить валидации)

## Как проверить
- `cargo test -p aether-core` + тест: манифест с абсолютным `allowed_paths` не включается
  ни обычным, ни force-путём.
- Ручной сценарий: packwiz (относительные пути, `apiVersion 0.2.0`) включается как раньше.

## Ловушки
- `validate` сейчас объединяет `runtime.validate()` и `api.validate()` — для force-пути их надо
  разделить, иначе force перестанет работать (F-12).
- Дефолтные `allowed_paths`, которые добавляет сам загрузчик (`/cache`, `/instances`),
  абсолютны на стороне хоста — валидация относится только к путям **из манифеста**.

## Проверка перед мержем (компенсация уровня модели)
Модель — Sonnet, поэтому обязательны:
1. Тест: force-enable по-прежнему обходит **только** проверку версии API, но не `RuntimeConfig::validate()`.
2. Ручная проверка: packwiz (`apiVersion 0.2.0`, относительные пути) включается как раньше.

## Осталось
— Ручной сценарий из раздела «Как проверить» (packwiz включается в реальном desktop-приложении
  как раньше) **не выполнен как живой GUI-прогон**: в этой сессии нет Tauri-окружения для
  клика по кнопке "Enable". Доступ к `../packwiz-plugin` изначально не давался, затем был
  разрешён в этой же сессии — по факту прочитан `packwiz/Cargo.toml`:
  `[package.metadata] api_version = "0.2.0"`, ключа `allowed_paths` нет вовсе (генератор
  `xtask` (`generate_plugin_manifest.rs`) в этом случае подставляет `Vec::default()`, т.е.
  пустой список), `features` там тоже нет → тоже пустой список. Добавлен тест
  `enable_succeeds_with_real_packwiz_manifest_values`, который прогоняет
  `EnablePluginUseCase::execute` ровно с этими значениями (`allowed_paths: vec![]`,
  `api: VersionReq::parse("0.2.0")`) через мок-загрузчик до состояния `Loaded`. Это доказывает
  структурно (не догадкой), что новый безусловный вызов `runtime.validate()` — no-op для
  реального манифеста packwiz (пустой `allowed_paths` тривиально проходит), а `^0.2.0`
  удовлетворяется текущим `PLUGIN_API_VERSION` (0.2.0 в `aether-core-plugin-api/Cargo.toml`),
  так что путь `check_compatibility` тоже не меняется. Не проверено вживую: фактическая загрузка
  собранного `packwiz.wasm` через `ExtismPluginLoader` и клик "Enable" в самом desktop-приложении.
  Если владелец считает исходное доказательство достаточным — можно перевести в `done` без
  дополнительного ручного шага; иначе нужен один живой прогон в desktop-приложении.
