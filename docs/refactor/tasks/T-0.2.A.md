Заведена по итогам T-0.2 (см. F-19). Решение Q4 требует помечать неверифицированный
плагин «в UI и в логе»; в T-0.2 сделан только лог, потому что список файлов карточки
T-0.2 — только ядро. Признак верификации сейчас никуда за пределы ядра не выходит.

## Что сделать
- Пробросить признак верификации из `Plugin` до фронта:
  `PluginVerificationStorage::get` → `Plugin` → `PluginDto` (ядро) → `PluginDto` (десктоп)
  → `bindings/plugin.ts`. Признак — именно «есть ли эталон», а не сам хеш.
- Перегенерировать биндинги (`generate-bindings`), не править `bindings/plugin.ts` руками.
- Показать в списке плагинов и на карточке плагина бейдж «не верифицирован» с пояснением:
  плагин установлен не через провайдера, целостность его `.wasm` не проверяется.

## Файлы
- `features/plugins/domain/models/plugin.rs`, `features/plugins/app/dtos.rs`
- `apps/desktop/src/features/plugins/infra/tauri/dtos/plugin.rs`
- `apps/frontend/src/entities/plugins/`, `apps/frontend/src/shared/api/bindings/plugin.ts`

## Как проверить
- `cargo test -p aether-core`, сборка фронта.
- Ручной сценарий: импортировать плагин из локального архива → бейдж «не верифицирован»;
  установить тот же плагин из GitHub-релиза → бейдж пропадает.

## Проверка перед мержем (компенсация уровня модели)
- Убедиться, что в DTO уезжает только булев признак: сам sha256 фронту не нужен и
  не должен утекать в биндинги.
- Убедиться, что `bindings/plugin.ts` перегенерирован, а не отредактирован вручную
  (файл начинается с «This file has been generated by Tauri Specta»).
