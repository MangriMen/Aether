# Протокол работы агента над рефакторингом установки контента

Этот файл — обязательный к прочтению для любого агента (любой модели), который продолжает работу
над рефакторингом подсистемы установки контента. Он короткий. Соблюдай его целиком.

## 1. Перед началом работы (всегда)

Прочитай в этом порядке:

1. `docs/refactor/STATUS.md` — единственный индекс задач и их статусов.
2. `docs/refactor/OPEN_QUESTIONS.md` — вопросы, ожидающие решения владельца. Если твоя задача
   зависит от открытого вопроса — **не начинай её**, переведи в `blocked` и сообщи владельцу.
3. Карточку своей задачи: `docs/refactor/tasks/<ID>.md`.
4. `refactoring_plan.md` — архитектурное решение (источник истины по «как должно быть»).
5. `docs/refactor/FINDINGS.md` — известные расхождения плана с кодом. Не переоткрывай их заново.

Справочные материалы (читать по необходимости, не обязательны): `plugin-architecture-audit.md`,
`audit_clarification.md`.

**Эти три файла — `refactoring_plan.md`, `plugin-architecture-audit.md`,
`audit_clarification.md` — обязаны лежать в корне репозитория и быть закоммичены.**
Если их нет в `git ls-files`, работа не начинается: сначала верни их в репозиторий.
Агент, открывший репозиторий с нуля, должен получить весь контекст из файлов, а не из переписки.

**История чата не является источником истины.** Всё состояние — только в файлах выше.

## 2. Во время работы

- Одна задача = один коммит/PR. Не делай «заодно» соседние задачи: если увидел проблему вне
  scope — запиши её в `FINDINGS.md` и/или заведи новую карточку со статусом `not_started`.
- **Не меняй зафиксированные архитектурные решения** из `refactoring_plan.md` (раздел
  «Принятые архитектурные решения» и «Что явно НЕ делаем»). Если в ходе работы решение
  оказывается невыполнимым или противоречит коду:
  1. Останови реализацию этой части.
  2. Добавь пункт в `docs/refactor/OPEN_QUESTIONS.md` с пометкой `НА СОГЛАСОВАНИЕ`.
  3. Переведи задачу в `blocked` и опиши в карточке, что именно заблокировано.
  Никогда не «чини» план молча в коде.
- Сразу при старте переведи статус задачи в `in_progress` в `STATUS.md` и в карточке.
- Если задача помечена «Ревью перед мержем: да» — не мержи сам, дождись владельца.

## 3. После завершения задачи (обязательно, до окончания сессии)

В карточке `docs/refactor/tasks/<ID>.md`:

1. Поставь статус (`done` / `blocked` / `needs_decision`).
2. Допиши строку в раздел «Журнал» в формате:
   `ГГГГ-ММ-ДД | <модель/агент> | <что реально сделано> | <коммит или "не закоммичено">`
3. В разделе «Осталось» перечисли то, что задумывалось, но не сделано (пустой список — тоже явная запись `— нет`).
4. Расхождения с планом, найденные по ходу, добавь в `docs/refactor/FINDINGS.md`
   (новый пункт `F-N`), а не в карточку.

В `docs/refactor/STATUS.md`: обнови статус в строке задачи и дату последнего изменения.

Ничего не удаляй из журналов — только дописывай.

## 4. Статусы

| Статус | Значение |
| --- | --- |
| `not_started` | не начато |
| `in_progress` | в работе прямо сейчас |
| `done` | сделано и проверено по разделу «Как проверить» |
| `blocked` | нельзя продолжать: ждёт другой задачи или внешнего фактора |
| `needs_decision` | нужно решение владельца (обязательно есть пункт в `OPEN_QUESTIONS.md`) |
| `ОТЛОЖЕНО` | задача остаётся в плане, но сознательно выведена из текущего прохода |

`ОТЛОЖЕНО` ставит только владелец. Не бери такую задачу в работу и не «разблокируй» её сам,
даже если её зависимости выглядят выполненными.

## 5. Границы репозиториев

Задачи затрагивают три репозитория:

- `aether` (этот) — ядро и десктоп.
- `packwiz-plugin` (`../packwiz-plugin`) — WASM-плагин packwiz.
- `curseforge-plugin` (`../curseforge-plugin`) — WASM-плагин CurseForge (пока не под git).

**Состояние и статусы ведутся только здесь**, в `aether/docs/refactor/`, даже для задач,
код которых лежит в репозитории плагина. В карточке всегда указан целевой репозиторий.

## 6. Проверка

Перед тем как ставить `done`, выполни ровно то, что написано в разделе «Как проверить»
карточки. Если проверку выполнить нельзя (нет окружения, нет ключа API и т.п.) — это не `done`,
а `blocked` с пояснением. Не пиши «проверено», если не запускал.

## 7. Как выбрать модель для задачи

У каждой карточки есть поле «Модель». Если заводишь новую задачу — классифицируй её по тем же
критериям. Доступны: **DeepSeek V4.1 Flash** (быстрая/дешёвая), **Claude Sonnet 5** (средний
уровень), **Claude Opus 5** (самый способный).

**DeepSeek V4.1 Flash** — механическая правка с однозначным решением: не требует понимания
малодокументированного поведения Extism и не меняет публичный контракт между плагином и ядром.
Сюда попадают точечные фиксы (zip-slip, вызов `with_memory_max`/`with_timeout` на правильном
типе), рутинный boilerplate (DTO-мапперы, сериализация) и задачи, где правильный ответ уже
полностью описан в карточке.

**Claude Sonnet 5** — нужно спроектировать код в рамках уже зафиксированной архитектуры, но без
неоднозначности в форме: новая host-функция по уже описанному контракту, миграция провайдера на
уже спроектированный трейт, доработка `InstallPlanExecutor` по уже утверждённой логике диффа.
Требует аккуратности с типами, lifetime и async в Rust, но не архитектурных решений.

**Claude Opus 5 + обязательное ревью владельца перед мержем** — если выполняется хотя бы одно:
- **(a)** задача сама формирует архитектурное решение, которым дальше пользуются другие задачи
  (доменные модели `InstallPlan`/`ProviderRef`, диффинг install/update, схема `hostFunctions`
  в манифесте);
- **(b)** задача касается security-границы (allowlist `run_command`, `http_get` без редиректов,
  проверка `allowed_hosts`, лимиты песочницы, единственный путь записи в инстанс);
- **(c)** задача опирается на поведение Extism, установленное только чтением исходников
  (см. `audit_clarification.md`).

Правила применения:
- Для каждой задачи на Flash или Sonnet в карточке есть раздел **«Проверка перед мержем
  (компенсация уровня модели)»** — он обязателен к выполнению, его нельзя пропустить.
- Задача с ревью (`Ревью перед мержем: да`) не мержится агентом: он останавливается и передаёт
  работу владельцу.
- Модель можно поднять (взять Opus вместо Flash), но не понизить: понижение — только через
  явное разрешение владельца, записанное в карточке.
